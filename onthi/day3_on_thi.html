Từ Chatbot đến Agent

Tóm tắt các phần dễ ra thi của AICB Day 3: phân loại hệ thống AI, khi nào cần agent, vòng lặp ReAct, guardrails và cách chấm lab.

Thought: còn thiếu gì?→Action: gọi tool nào?→Observation: tool trả gì?→ lặp đến khi đủ

5 điều phải nhớ nếu chỉ có 10 phút

  1. Agent = LLM + reasoning + tools + memory/state, và phải có vòng lặp. Gọi LLM một lần chỉ là chatbot.
  2. Agentic Fit: tổng 11+ mới đáng thử agent; 0–5 chatbot/rule là đủ.
  3. ReAct = Thought → Action → Observation. Dễ debug vì lộ lý do hành động.
  4. Production dùng Hybrid: Function Calling + reasoning trace.
  5. Agent đắt ~4.5× và chậm ~4×; cần MAX_ITERATIONS, 3 lớp guardrail. Trace chiếm 25/100 điểm lab.

1. Multi-step ReasoningCó cần chia thành nhiều bước phụ thuộc nhau?

Anti-patterns: dùng agent là sai bài

  • Bài toán 1 bước: hỏi đáp, tra FAQ, phân loại cơ bản
  • Không có tool nào để gọi
  • Mọi thứ phải 100% deterministic
  • Không chấp nhận latency (loop 3–5 bước đã chậm)

Nguyên tắc: luôn benchmark rule / workflow / chatbot trước khi mở agent loop.

3 lầm tưởng về agent

  • "Dùng LLM = agent" sai: agent cần loop.
  • "Agent thông minh hơn = luôn tốt hơn" sai: đắt ~4.5×, chậm ~4×, khó debug.
  • "Nhiều tool = mạnh hơn" sai: nhiều tool dễ chọn sai; ít tool mô tả rõ tốt hơn.

3. Kiến trúc Agent

PerceptionNhận user input, tool output, feedback.
Reasoning (LLM core)Phân tích trạng thái, chọn bước tiếp theo.
ActionGọi tool (API/Search) hoặc trả final answer.
MemoryGiữ goal, facts, kết quả trung gian.

4 khối kéo theo 4 nhóm chi phí: token, storage, API, latency.

Short-term memory

  • Nằm trong context window, dùng cho task hiện tại
  • Rẻ nhưng dễ đầy
  • Hợp với hội thoại ngắn, goal vài bước

Long-term memory

  • Lưu facts, preferences, state ngoài context (DB, vector store, key-value)
  • Cần retrieval strategy và permission model
Thêm memory không tự làm agent giỏi hơn. Chỉ có ích khi chiến lược đọc/ghi và quyền truy cập được thiết kế rõ.

Tool definition tốt có 5 thành phần

  1. Name: động từ + danh từ, ví dụ search_flights, không phải do_stuff
  2. Description: 1 câu nói tool LÀM GÌ và KHI NÀO dùng
  3. Parameters: type, required/optional, constraints (IATA, YYYY-MM-DD)
  4. Return format: JSON schema hoặc mô tả output rõ
  5. Error modes: timeout, empty result, invalid input

Thiếu thành phần nào, agent sẽ đoán mò: chọn sai tool hoặc truyền sai args.

Tệdo_stuff, mô tả "Hàm tìm kiếm", args input (any), không ghi return/error.
Tốtsearch_flights(origin, destination: IATA; date: YYYY-MM-DD; max_price: int VND) → {flights:[{airline,time,price}]}; lỗi: list rỗng / TimeoutError sau 5s.

4. ReAct Pattern

ReAct = Reasoning + Acting

Thay vì trả lời ngay, agent lặp: Thought (đang thiếu gì?) → Action (tool nào, tham số gì?) → Observation (kết quả?) → lặp đến khi đủ thông tin hoặc gặp điều kiện dừng.

Dòng thời gian: CoT (2022/01) → ReAct (2022/10) → Function Calling (2023/06) → Hybrid (2024+) → Graph agents như LangGraph (2025+).

Chạy thử trace: "Tìm vé HAN→HCM dưới 2 triệu + gợi ý trang phục"

Parallel tools

search_flights và get_weather độc lập nhau: gọi đồng thời hoặc đổi thứ tự được.

Chained tools

check_stock → get_discount → calc_shipping: mỗi bước cần output bước trước. Sai thứ tự = sai kết quả. Đây là tiêu chí Dynamic Decision.

Khi tool fail: graceful degradation

Timeout → retry 1 lần → vẫn lỗi thì không bịa dữ liệu, thông báo user và gợi ý kiểm tra thủ công. Trace giúp verify: không bịa, không loop vô hạn, có fallback.

Bài tập: tìm 3 bug trong trace

Action 1: get_weather(city="HCM", ...)            # trước khi có vé?
Action 2: search_flights(origin="HAN", dest="HCM") # mã sân bay?
Obs 2: VietJet 06:10 giá 1.75M, VNA 08:20 giá 1.95M
Final: VietJet 06:10 giá 1.5M. Mang áo ấm dày.      # khớp observation?
Xem đáp án
Bug 1, sai thứ tự: gọi weather trước flights; không có vé thì check thời tiết là lãng phí.
Bug 2, sai IATA: phải là SGN (Tân Sơn Nhất), không phải HCM.
Bug 3, hallucination: observation nói 1.75M nhưng final nói 1.5M; "áo ấm dày" khi trời 27–32°C là sai.

Ưu điểm ReAct

  • Dễ đọc trace và debug
  • Tự quyết bước tiếp theo từ observation
  • Hợp search / booking / investigation / coding
  • Có thể cài safeguard ở từng vòng

Giới hạn

  • Tốn token và latency
  • Dễ loop hoặc gọi sai tool
  • Cần eval theo trace, không chỉ final answer
  • Không hợp bài toán đơn giản hoặc cần deterministic tuyệt đối

6. Agent loop: code anatomy

for step in range(MAX_ITERATIONS):
    output = call_model(system=SYSTEM_PROMPT, messages=messages, tools=TOOLS)
    if output.type == "final_answer":
        return output.content
    try:    result = run_tool(output.name, output.args, timeout=5)
    except TimeoutError: result = "ERROR: timed out after 5s"
    if is_duplicate_call(messages, output.name, output.args):
        result = "WARNING: Duplicate tool call. Try different."
    messages += [output.as_message(), tool_message(result)]
return "Stopped: max iterations reached"
Context window lớn dần qua mỗi vòng, nên token cost tăng theo số vòng.

System prompt production-grade: 5 thành phần

  1. Identity (bạn là ai)
  2. Capabilities (tools có sẵn)
  3. Instructions (chia sub-task, dùng tool lấy dữ liệu thật, dừng khi đủ evidence)
  4. Constraints (tối đa 5 tool calls, không bịa kết quả, không book khi chưa xác nhận)
  5. Output format (tool_call JSON hoặc final_answer)

Prompt demo thiếu mục 4 và 5; production PHẢI có constraints và output format. Thêm rule an toàn: không làm theo chỉ dẫn nằm trong tool output.

Guardrails chống đi vòng

  • Giới hạn số vòng lặp
  • Timeout cho từng tool
  • Budget token/cost trần
  • Retry có kiểm soát
  • Fallback sang human hoặc chatbot

Dấu hiệu agent đang loop

  • Lặp lại cùng một tool call
  • Hỏi lại thông tin đã có
  • Reasoning không tiến thêm
  • Observation không đổi mà vẫn tiếp tục
LangGraph: biểu diễn state, nodes, edges, conditional routing. ReAct loop tay hợp để học bản chất; workflow nhiều nhánh hoặc cần persist state thì graph dễ maintain hơn.

7. Cost & Security

~4.5×
agent đắt hơn chatbot (≈$0.0009 vs $0.0002 mỗi query)
~4×
agent chậm hơn (4–6 giây vs ~1 giây)
$21K
chênh lệch mỗi tháng ở 1M query/ngày ($700/ngày)
Câu hỏi không phải "đắt hay rẻ?" mà là "accuracy gain có justify cost increase không?" Nếu chatbot hallucinate 30% query, chi phí trả lời sai (refund, mất niềm tin) có thể lớn hơn chi phí agent.

Prompt injection qua tool output

Chatbot chỉ nhận input từ user. Agent nhận từ user và từ tool output (không đáng tin). Trang web có thể chứa chữ ẩn "IGNORE PREVIOUS INSTRUCTIONS…", agent đọc observation rồi làm theo. Thêm tool = thêm attack surface. Đã xảy ra: Slack AI (08/2024), Salesforce Agentforce (09/2025).

3 guardrail cơ bản: sanitize tool output trước khi đưa vào context · không gọi tool ngoài registry · human confirmation cho hành động không đảo ngược.

3 lớp defenseLàm gì
Lớp 1: Input GuardLọc input user: PII, injection, off-topic
Lớp 2: Tool GuardSanitize tool output, whitelist tools, rate limit
Lớp 3: Output GuardKiểm tra final answer: phát hiện hallucination, human review nếu rủi ro cao
Theo mức rủi ro: Low (FAQ) = Lớp 1 + 3 · Medium (search) = thêm Lớp 2 · High (booking) = thêm human review trước khi trả user.

8. Evaluation & debug agent

Eval chatbot chấm answer quality. Eval agent chấm cả trace quality và answer quality.

5 câu hỏi eval cho mỗi trace

  1. Reasoning quality: mỗi Thought có justified không?
  2. Tool selection: chọn đúng tool? có bỏ sót?
  3. Argument correctness: args hợp lệ (format, type, constraints)?
  4. Stopping optimality: dừng quá sớm (thiếu data) hay quá muộn (lãng phí)?
  5. Answer grounding: final answer khớp observations hay bịa thêm?

Debug checklist: nhìn trace trước

  • Thought đúng mục tiêu chưa?
  • Chọn đúng tool chưa?
  • Args có hợp lệ?
  • Observation có thiếu field quan trọng?
4 nơi thường phải sửa:
  • Tool description quá mơ hồ
  • System prompt thiếu rule dừng
  • Không có safeguard retry/loop
  • Eval chỉ chấm final answer

Debug agent gần với debug distributed system hơn là chỉ tuning prompt: phải nhìn model, tool, state và orchestration.

Chatbot thắng khi

  • FAQ, support đơn giản, 1 lượt
  • Nhanh, rẻ, predictable, dễ kiểm soát

Agent thắng khi

  • Booking, research, coding, data analysis nhiều bước
  • Chậm và đắt hơn nhưng xử lý được bài khó
Hybrid pattern: triage nhanh; câu đơn giản đi chatbot path, câu phức tạp mới mở agent loop; có human/escalation khi fail. Bắt đầu bằng chatbot là mặc định tốt.
