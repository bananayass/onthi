1. Single-agent hay Multi-agent?

Single-agent là gì?

Một agent/model đảm nhận các bước cần thiết để hoàn thành việc. Nó có thể gọi tool và truy xuất RAG, nhưng vẫn phải tự quản lý phần lớn thông tin trong context và quyết định luồng làm việc.

4 giới hạn cốt lõi của single-agent

1. Context bottleneck

Yêu cầu, lịch sử, kết quả tool và bằng chứng cùng chen vào một context window có giới hạn.

2. Specialization trade-off

Prompt ôm càng nhiều vai càng dài; agent khó làm thật tốt tất cả vai trò.

3. Parallelism hạn chế

Nhiều phần việc độc lập vẫn có thể bị chạy lần lượt, làm tăng độ trễ không cần thiết.

4. Reliability yếu

Hiểu sai từ bước đầu có thể kéo lệch cả luồng; khó xác định chính xác bước gây lỗi nếu thiếu trace.

Khi nào cân nhắc Multi-agent?

  • Công việc có nhiều vai chuyên môn khác nhau.
  • Có các phần độc lập có thể chạy song song.
  • Cần thay hoặc thêm worker mà không viết lại một prompt khổng lồ.
  • Cần khoanh vùng lỗi theo từng bước/worker rõ ràng.
Không nên dùng chỉ vì nghe “xịn”. Mỗi agent bổ sung thường đồng nghĩa thêm LLM call, token, độ trễ và điểm có thể hỏng. Slide nhấn mạnh multi-agent là một đánh đổi, không phải mặc định.

Agents-as-tools vs Handoff

Agents-as-tools

Agent A gọi agent B như một công cụ. B trả kết quả về A; A giữ cuộc hội thoại và tiếp tục trả lời người dùng.

Agent A→Agent B→Kết quả về A

Handoff

Agent A chuyển quyền điều khiển cho agent B. B tiếp quản phần hội thoại còn lại.

Agent A⇢Agent B→Tiếp tục xử lý
Câu hỏi phân biệt: “Sau lần gọi này, ai nói tiếp với user?” Agent gọi tiếp nếu agents-as-tools; agent mới tiếp quản nếu handoff.

Lỗi khi ghép kết quả

  • Workers cùng ghi một key trong cùng bước có thể tạo xung đột. LangGraph báo “Can receive only one value per step” nếu không có reducer phù hợp.
  • Nếu ghép tất cả output bằng chuỗi dài, context sẽ phình ra. Worker nên trả kết luận ngắn, có cấu trúc; supervisor tổng hợp.
  • Worker trả `None`/không có kết quả không được giả định là thành công. Dùng envelope có `status`, `data`, `error` hoặc trường tương đương.

3. Supervisor–Worker và Shared State

User request→Supervisor
phân tích + route→Worker chuyên biệt→Supervisor tổng hợp
answer + trace

Trách nhiệm đúng vai

Supervisor
  • Phân tích yêu cầu.
  • Chọn worker cần gọi.
  • Theo dõi trạng thái, retry khi hợp lý.
  • Tổng hợp output cuối.
  • Biết khi nào phải xin người duyệt.
Worker
  • Chuyên một năng lực chính.
  • Input/output rõ ràng để test độc lập.
  • Nếu có thể, ít phụ thuộc lịch sử toàn hệ thống.
  • Lỗi cục bộ không nên làm sập cả graph.

Anti-pattern cần nhớ

Ví dụ State cho trợ lý hoàn tiền

class RefundState(TypedDict):
    task: str                         # yêu cầu ban đầu
    order_id: str | None              # mã đơn
    policy_chunks: list                # bằng chứng chính sách
    order_status: dict | None          # kết quả tra đơn
    draft_answer: str | None           # câu trả lời nháp
    status: str                        # pending/running/done/error
    trace: list                        # log các node
Quy tắc thiết kế state: field nào có thể thì nên có một nơi ghi chính; trường `trace` là ngoại lệ thường cần nối thêm bằng reducer. Tách kết quả từng worker thành trường riêng để có thể test độc lập.

4. MCP — kết nối agent với tool/năng lực bên ngoài

MCP trả lời: “Agent lấy năng lực/công cụ ở đâu và gọi theo giao thức nào?”

Trước MCP và khi dùng MCP

Không có chuẩn chung

Mỗi tool, mỗi API, mỗi framework có thể cần adapter/tích hợp riêng.

Có MCP

Client và server nói chuyện theo giao thức chuẩn; server công bố năng lực, client khám phá và gọi tool.

Luồng gọi tool được mô tả trong slide

1. Khám phá server→2. `tools/list`→3. Đọc schema→4. Chọn tool→5. `tools/call`→6. Kết quả

Thông tin quan trọng của tool gồm tên, description và `inputSchema`; client dùng chúng để biết tool làm gì và input phải có dạng nào.

Transport theo slide

  • stdio: dùng cho server local.
  • Streamable HTTP: dùng cho server remote.
  • Slide ghi HTTP+SSE là deprecated theo phiên bản spec được trình bày, đồng thời nhấn mạnh cần pin phiên bản và đọc changelog trước khi nâng SDK.

MRTR — nhiều vòng hỏi/đáp

Nếu server cần thêm thông tin đầu vào, nó có thể trả `InputRequiredResult`; client hỏi người dùng/lấy thông tin rồi gửi lại bằng `inputResponses`. Ý tưởng: yêu cầu thêm dữ liệu theo giao thức thay vì đoán hoặc thất bại ngay.

Agent Card

Trong slide, A2A Agent Card là hồ sơ mô tả một agent, nằm ở `/.well-known/agent-card.json` theo v1.0, công bố các interface được hỗ trợ và thông tin cần để bên khác biết cách kết nối.

Message contract tối thiểu

`task`

Giao việc gì?

`context`

Agent nhận cần biết thông tin nào để làm đúng?

`expected_output`

Kết quả cần trả về theo format nào?

Need-to-know: gửi thiếu context cần thiết thì worker làm sai; gửi quá nhiều thì tốn token và có thể lộ dữ liệu không cần thiết. Chỉ truyền thông tin đủ cho nhiệm vụ.

Ví dụ message contract: Fraud-check

{
  "task": "Kiểm tra dấu hiệu gian lận cho yêu cầu hoàn tiền",
  "context": {
    "order_id": "A123",
    "order_status": "delivered",
    "refund_amount": 850000,
    "signals": ["nhiều yêu cầu hoàn tiền gần đây"]
  },
  "expected_output": {
    "risk_level": "low | medium | high",
    "reasons": ["lý do có bằng chứng"],

}

Đây là ví dụ minh họa do tài liệu ôn tập diễn giải theo message contract task/context/expected_output; không phải schema bắt buộc chính thức của A2A.

Cách nhớ “A2A loves MCP”

Ứng dụng có thể dùng A2A để giao việc cho agent khác; mỗi agent vẫn có thể dùng MCP của riêng mình để gọi tool. Hai giao thức giải quyết hai lớp kết nối khác nhau.

6. LangGraph: node, edge, state, persistence

Node = ai làm?

Một hàm Python nhận state và trả về các phần state cần cập nhật.

Edge = đi đâu?

Luồng nối giữa các node. Có thể cố định hoặc conditional dựa vào state.

State = biết gì?

Dữ liệu được truyền giữa các node; kiểu có thể định nghĩa bằng TypedDict/Pydantic.

Ví dụ routing

def route(state) -> str:
    if state["need_tool"]:
        return "tool_worker"
    if state["need_retrieval"]:
        return "retrieval_worker"
    return "synthesis_worker"

 g = StateGraph(AgentState)
 g.add_node("supervisor", supervisor_node)
 g.add_edge(START, "supervisor")
 g.add_conditional_edges("supervisor", route)
 app = g.compile()

Hãy đọc hàm `route` như một biển chỉ đường: kiểm tra trạng thái, rồi quyết định chuyển đến node nào. `add_conditional_edges` kết nối quyết định đó vào graph.

Checkpointer, thread_id và interrupt

  • Checkpointer: lưu trạng thái để graph có thể tiếp tục thay vì mất hết sau khi dừng.
  • thread_id: định danh một cuộc chạy/cuộc hội thoại. Cùng `thread_id` thì tiếp tục cùng luồng state đã lưu.
  • `interrupt()`: tạm dừng để xin quyết định của con người.
  • Resume: chạy tiếp sau khi có quyết định.
  • Idempotent side effect: khi resume, node có thể chạy lại; hành động bên ngoài cần thiết kế sao cho chạy lặp không gây tác dụng phụ trùng lặp.
Ví dụ dễ hiểu: nếu node gửi email xong rồi workflow bị dừng, khi resume có thể chạy lại node gửi email. Nếu không có cơ chế chống trùng, khách có thể nhận hai email. Đây là lý do slide nhắc side effect khi resume phải idempotent.

Worker output là dữ liệu không tin cậy

Subagent có thể mang nội dung từ web, file hoặc tool bên ngoài trở về. Kể cả worker nội bộ, output của nó vẫn phải được xem như dữ liệu đầu vào cần kiểm tra, không phải chỉ dẫn đáng tin.

Không làm: “worker A bảo bỏ qua chính sách nên supervisor cứ làm theo.”
Nên làm: kiểm tra output, nguồn gốc và quyền hạn; không để nội dung trong báo cáo ghi đè instruction hoặc policy.

7. Observability, trace và chi phí

Không có trace thì debug multi-agent gần như mò mẫm.

Ba câu hỏi mà trace cần trả lời

  1. Agent nào đã chạy, theo thứ tự nào?
  2. Input/output ở từng bước là gì?
  3. Lỗi hoặc cảnh báo gì đã xảy ra?

Một trace entry tốt

{
  "t": "14:03:21",
  "agent": "supervisor",
  "action": "route",
  "decision": "retrieval_worker",
  "reason": "hỏi về chính sách",
  "status": "ok",
  "latency_ms": 312
}

Ví dụ này cho thấy không chỉ ghi “OK”, mà còn ghi agent, hành động, quyết định, lý do, trạng thái và độ trễ. Slide gợi ý bắt đầu bằng JSON log rồi mới tích hợp công cụ quan sát như LangSmith, Langfuse, Arize Phoenix hoặc OpenLLMetry.

Trace không đồng nghĩa hệ thống đúng

Một node có thể chạy thành công về mặt kỹ thuật (`status: ok`) nhưng đưa ra câu trả lời sai vì bỏ sót worker hoặc thiếu dữ liệu. Debug phải kiểm tra cả ý nghĩa của dữ liệu, không chỉ xem có exception hay không.

Ví dụ hoàn tiền sai trong slide

Yêu cầu: “Đơn A123 mua 10 ngày trước có được hoàn tiền không?”

Trace ghi nhận: supervisor gọi policy_worker → tìm thấy “Hoàn tiền trong 7 ngày…” → synthesis_worker nhận `policy_chunks=3`, nhưng `order_status=None`.

Điểm đáng ngờ: supervisor bỏ qua order worker; synthesis vẫn kết luận “Có” dù thiếu trạng thái đơn. Tất cả node báo `ok` nhưng câu trả lời không được chứng minh.

Cách xử lý: yêu cầu đủ dữ kiện bắt buộc trước khi kết luận; nếu `order_status` là `None`, tra cứu lại hoặc nói rõ chưa đủ thông tin.

Chi phí

Multi-agent làm tăng số model call và token. Slide đưa ra số liệu minh họa từ tài liệu tham khảo: multi-agent có thể dùng token nhiều lần hơn so với một lần chat và không phải tác vụ nào cũng được lợi.

Đừng học thuộc con số như quy luật tuyệt đối. Tỷ lệ phụ thuộc mô hình, số worker, context, tool và cách tính trong benchmark. Ý cần nhớ là: nhiều agent = thêm compute/chi phí; chỉ đáng dùng khi lợi ích từ chia việc, song song hoặc context chuyên biệt đủ lớn.

8. An toàn, harness và quyền hạn

Ba nhóm lỗi multi-agent theo slide

NhómTỷ lệ được nêu trong slideVí dụ
Thiết kế hệ thống44,2%Lặp vô hạn, không biết khi nào dừng, làm sai luồng.
Lệch pha giữa agent32,3%Agent hiểu một đường, agent khác làm đường khác; nhiệm vụ bị trôi.
Không kiểm chứng23,5%Kiểm tra sai/thiếu, hoặc kết thúc quá sớm.

Các tỷ lệ trên là số liệu được trích trong bộ slide; chúng mô tả nghiên cứu/trace cụ thể chứ không khẳng định tỷ lệ lỗi của mọi hệ multi-agent.

Bộ ba nguy hiểm (“lethal trifecta”)

Slide mô tả rủi ro khi hệ thống kết hợp ba yếu tố:

1. Đọc dữ liệu riêng tư

Ví dụ worker đọc CRM hoặc email nội bộ.

2. Nhận nội dung không tin cậy

Ví dụ email/web có prompt injection.

3. Có đường gửi dữ liệu ra ngoài

Ví dụ supervisor có tool gửi email hoặc đăng nội dung.

Điểm mấu chốt: không agent nào riêng lẻ cần có cả ba khả năng; hệ thống vẫn nguy hiểm nếu các khả năng kết hợp qua nhiều worker. Phải kiểm tra quyền trên toàn hệ thống, không chỉ từng agent tách biệt.

Hành động không hoàn tác được cần duyệt

Ví dụ trong slide: xóa database production, gửi email ra ngoài, thay đổi dữ liệu thật. Đây không chỉ là lỗi “ảo giác”; đó có thể là quyền ghi trong hệ thống mà thiếu cổng duyệt.

Harness là gì?

Agent = Model + Harness. Model đưa ra đề xuất; harness cung cấp môi trường chạy, tool access, sandbox, giới hạn quyền, kiểm tra, trace và cổng phê duyệt.

Model

Hiểu yêu cầu, suy luận, đề xuất gọi tool hoặc trả lời.

Harness

Quy định tool nào được gọi, dữ liệu nào được chạm tới, ngân sách/vòng lặp, nơi chạy, log và khi nào cần human approval.

Thông điệp của slide: nếu hệ thống chạy kém, trước khi đổi model hãy kiểm tra harness và cách chia vai.

Cổng quyết định tool

Quyết địnhÝ nghĩa khái quát
ALLOWCho thực hiện hành động nằm trong quyền đã cho.
ASKTạm dừng để xin phê duyệt.
DENYTừ chối hành động không được phép.
DRY_RUNChạy mô phỏng/preview để xem điều gì sẽ xảy ra mà chưa thực hiện thay đổi thật.

Các nhãn này được dùng ở đây như cách ghi nhớ thực hành về cổng hành động; luôn theo đúng policy cụ thể của hệ thống khi triển khai.

9. Cách debug một hệ Multi-agent

Đừng nhảy ngay đến kết luận “model yếu”. Hãy tìm đúng lớp phát sinh vấn đề.

1
Prompt / Role: worker có hiểu đúng trách nhiệm và output contract không?
2
Context / Input: worker có nhận đủ thông tin cần thiết, đúng nguồn và đúng thời điểm không?
3
Routing / Loop: supervisor chọn đúng worker chưa, có vòng lặp hoặc kết thúc quá sớm không?
4
Harness / Permission: tool có quá nhiều quyền không, hành động có cần approval không, output không tin cậy có bị làm theo không?
5
Evaluation / Trace: có testcase tái hiện lỗi chưa, phiên bản sửa có pass case lỗi cũ và không làm hỏng case khác không?

Checklist trước khi đưa vào production

  • Vai trò và output của mỗi worker viết rõ ràng.
  • State schema có trạng thái `pending/running/done/error` hoặc tương đương.
  • Biết điều kiện thành công và điều kiện dừng.
  • Có giới hạn vòng lặp, timeout và đường fallback.
  • Log input/output, quyết định routing, lỗi và latency; hạn chế log dữ liệu nhạy cảm.
  • Worker output được xem là dữ liệu cần kiểm tra.
  • Quyền theo nguyên tắc tối thiểu; hành động khó hoàn tác có phê duyệt.
  • Resume không làm lặp side effect ngoài ý muốn.
  • Chạy lại test cũ sau mỗi thay đổi.

10. Bảng ghi nhớ trước khi thi

Đề hỏiÝ trả lời cần nhớ
Khi nào dùng multi-agent?Khi cần chuyên môn hóa, song song hóa việc độc lập hoặc chia context; không dùng chỉ vì muốn “thông minh hơn”.
Supervisor làm gì?Phân tích yêu cầu, route, theo dõi trạng thái/retry, tổng hợp và quyết định lúc cần người duyệt.
Worker tốt có đặc điểm gì?Chuyên biệt, input/output rõ, test độc lập được, ít phụ thuộc state ngầm.
Agents-as-tools vs Handoff?Agents-as-tools trả kết quả về agent gọi; handoff chuyển quyền điều khiển sang agent nhận.
MCP vs A2A?MCP: agent–tool/capability. A2A: agent–agent, có task và message contract.
Node / Edge / State?Node = ai làm; edge = đi đâu; state = hệ thống biết gì.
Checkpointer / thread_id?Checkpointer lưu trạng thái; thread_id nhận diện cùng một luồng để tiếp tục.
interrupt()?Tạm dừng workflow để nhận quyết định, ví dụ human review; sau đó resume.
Vì sao side effect cần idempotent?Node có thể chạy lại khi resume/retry; idempotency giúp tránh hành động bị lặp.
Trace dùng làm gì?Truy vết thứ tự agent, input/output, quyết định, cảnh báo, lỗi và độ trễ.
Vì sao node “ok” mà kết quả sai?Không có exception không có nghĩa logic đúng; có thể thiếu dữ kiện hoặc sai routing.
Rủi ro trên toàn hệ?Dữ liệu riêng tư + input không tin cậy + công cụ gửi ra ngoài có thể kết hợp qua nhiều agent.
Hành động nào cần approval?Hành động nhạy cảm/khó hoàn tác như xóa dữ liệu production hay gửi thông tin ra ngoài.
Debug hệ agent bắt đầu từ đâu?Kiểm tra vai trò, context, routing/loop, harness/quyền, trace/eval; không vội đổi model.
Mẹo trả lời miệng: Nêu định nghĩa một câu → phân biệt với khái niệm gần giống → đưa ví dụ một dòng → nói một giới hạn/rủi ro.
