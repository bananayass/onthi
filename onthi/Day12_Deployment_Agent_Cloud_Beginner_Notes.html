Điều cốt lõi của Day 12

Agent chạy tốt trên localhost chưa có nghĩa là đã sẵn sàng cho 100 người dùng. Khi đưa lên cloud, ta phải nghĩ thêm về thời gian chạy, trạng thái, an toàn, độ tin cậy và hóa đơn token.

Ví dụ dễ hiểu: localhost như nấu ăn trong bếp nhà mình. Production giống mở quán: ngoài nấu được, còn phải phục vụ nhiều khách, xử lý lúc hết nguyên liệu, bảo vệ tiền và đảm bảo quán không đóng cửa khi bạn rời đi.

2. Docker & containerization

Container đóng gói ứng dụng, thư viện phụ thuộc và runtime thành một đơn vị có thể chạy trên laptop hoặc cloud. Mục tiêu là giảm tình trạng “it works on my machine”.

Dockerfile mẫu theo hướng slide

FROM python:3.12-slim AS builder
# Cài uv và dependencies theo lock file
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-install-project --no-editable

FROM python:3.12-slim AS runtime
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
ENV PATH="/app/.venv/bin:$PATH"
RUN useradd -m app && chown -R app /app
USER app
CMD ["fastapi", "run", "main.py", "--host", "0.0.0.0"]
Đừng quên: Dockerfile thực tế cần phù hợp với project của bạn. Thêm .dockerignore; không copy file .env hay API key vào image. Dùng USER app để tránh chạy root. Slide khuyến nghị mục tiêu image dưới 500 MB cho lab.

3. Request dài, streaming và state

Timeout: vì sao agent hay bị 504?

Gateway/proxy có thể ngắt kết nối trước khi agent hoàn thành reasoning loop. Slide minh họa giới hạn như API Gateway khoảng 29 giây, proxy idle khoảng 60 giây ở một số cấu hình, trong khi một agent có thể cần lâu hơn.

SSE — gửi token dần

Hợp khi client cần thấy nội dung tăng dần. Server gửi event theo luồng một chiều; để ý proxy buffering và gửi heartbeat khi agent im lặng lâu.

Async job — xử lý nền

Client gửi job, API trả job_id nhanh; client poll hoặc nhận webhook khi hoàn thành. Hợp tác vụ dài, batch hoặc không cần kết quả tức thì.

Gợi ý từ slide: Với SSE, proxy buffering có thể gom token lại; cần tắt buffering phù hợp, ví dụ X-Accel-Buffering: no. Nếu cần hỗ trợ reconnect, có thể lưu các token theo streamId để replay.

Stateful nhưng process phải stateless

Hai điều này không mâu thuẫn: instance không giữ state lâu dài trong RAM; state của phiên được lưu bên ngoài và nạp lại khi cần.

# Ví dụ cấu hình checkpoint LangGraph
config = {"configurable": {"thread_id": "session-123"}}
# Checkpoint được lưu ngoài process, ví dụ PostgresSaver
Ví dụ: Request đầu chạy ở Instance A, request tiếp theo có thể chạy ở Instance B. Nếu hội thoại nằm trong Redis/Postgres/checkpointer và có khóa phiên ổn định, B vẫn tiếp tục được.

Concurrency và cold start

  • Concurrency: agent thường I/O-bound vì chờ model/API. Nhiều request có thể chờ trong khi CPU thấp; cân nhắc scale theo concurrency hoặc queue depth.
  • Async: hữu ích khi chờ I/O, nhưng lời gọi blocking trong async def có thể nghẽn event loop.
  • Cold start: tải thư viện hoặc model nặng làm khởi động chậm; có thể giữ instance ấm hoặc lazy-load phần ít dùng.
Đừng nhầm health probe: Liveness = “còn sống?” fail có thể restart. Readiness = “đang sẵn sàng nhận traffic?” fail thì gỡ khỏi load balancer, không nhất thiết restart. Startup probe dành cho ứng dụng khởi động lâu.

5. Chọn cloud và managed runtime

Slide chia lựa chọn thành bốn tier theo mức độ phải tự quản hạ tầng. Với lab, khuyến nghị bắt đầu Tier 1 để hiểu quy trình containerize/deploy; sau đó nâng cấp khi nhu cầu thật sự đòi hỏi.

TierVí dụ trong slideKhi cân nhắc
Tier 0 — managed agent runtimeBedrock AgentCore, Vertex/Agent Runtime, Azure AI Foundry AgentMuốn ship nhanh, managed session/memory/identity, giảm gánh nặng vận hành.
Tier 1 — platform dễ deployRailway, Render, Fly.ioMVP/demo, kết nối repo và có public URL nhanh.
Tier 2 — cloud có autoscalingCloud Run, ECS FargateCần kiểm soát production và scaling hơn.
Tier 3 — control tối đaKubernetes / self-managedTeam có năng lực vận hành, network/compliance riêng, tối ưu ở quy mô lớn.

Framework ≠ Runtime: framework là thư viện/cách bạn viết agent; runtime là môi trường chạy, cấp session, storage, identity, scaling và vận hành. Đổi framework thường là refactor code; đổi runtime thường là thay cách deploy/vận hành.

Chọn platform theo workload: không chỉ nhìn giá. Kiểm tra request timeout, giới hạn runtime/session, SSE, state persistence, scale-to-zero, GPU và cách tính phí khi agent đang chờ model. Các số giới hạn/giá trong slide là ảnh chụp theo thời điểm của tài liệu, cần kiểm tra tài liệu nhà cung cấp trước khi triển khai.

Railway lab flow: kết nối GitHub repo → thiết lập environment variables → deploy → kiểm tra logs → lấy public URL → gọi thử endpoint qua HTTPS.

6. Hosting MCP server an toàn

stdio — local

Client khởi chạy MCP server như subprocess; giao tiếp qua stdin/stdout. Thường hợp dev/desktop, secret lấy từ môi trường.

Streamable HTTP — remote

Server chạy như service riêng, phục vụ nhiều client. Cần host và bảo vệ như một API thật; slide nêu OAuth 2.1 cho remote MCP.

Luồng kiến trúc nhớ nhanh: Registry để tìm → Gateway để gom và kiểm soát → Runtime để chạy. Registry cung cấp metadata/discovery, không có nghĩa server đã đáng tin.

Ba bẫy bảo mật quan trọng trong slide

  1. Token passthrough: MCP server không nên nhận token không được cấp riêng cho nó rồi chuyển nguyên token xuống service khác. Việc này có thể làm hỏng audit và giới hạn tốc độ.
  2. Confused deputy: xác thực đúng user chưa chắc client được quyền làm thay user đó. Cần kiểm tra client/permission theo từng flow.
  3. Route không đồng nhất: bảo vệ /mcp nhưng quên một route phụ như /mcp_message vẫn có thể để lộ tool. Xác thực mọi route.
Nguyên tắc: Remote MCP = API public hoặc nội bộ có thể bị tấn công. Dùng auth, phân quyền, container isolation, non-root và egress allowlist; không phơi CLI ra Internet một cách vô tình.

7. API gateway, security và cost protection

Luồng nên chạy trước mỗi request

  1. Authentication: xác định ai đang gọi.
  2. Rate limiting: giới hạn tốc độ/request theo user hoặc tenant.
  3. Input validation + budget admission control: kiểm tra dữ liệu, token ước tính và ngân sách trước khi gọi model.
  4. Agent: chỉ xử lý khi request được phép.

Cost guard tối thiểu — ý tưởng

estimated_cost = (
    input_tokens / 1_000_000 * input_price
    + max_output_tokens / 1_000_000 * output_price
)

if estimated_cost > MAX_USD_PER_REQUEST:
    reject_request()  # chặn trước khi gọi model
else:
    call_model()

Tag từng lần gọi theo user/tenant, workload và model; theo dõi token có thẩm quyền; đặt hard limit. “Spend alert” chỉ báo sau khi tiêu tiền, không thay thế admission control chặn trước.

Router và cache

  • LLM gateway/router: một endpoint gọi nhiều provider/model, hỗ trợ failover, retry/backoff, load balance và cost tracking.
  • Prompt caching: tái sử dụng prefix giống nhau, như system prompt/context cố định.
  • Semantic cache: dùng độ tương tự ngữ nghĩa để trả lời câu hỏi tương tự, nhưng có nguy cơ trả dữ liệu cũ; phải xét freshness.
Secrets: không commit API key vào Git hoặc Docker image. Nếu key đã lộ, thu hồi/revoke và tạo key mới. CORS chỉ kiểm soát một phần hành vi trình duyệt, không phải lớp auth.

8. Scaling, reliability và monitoring nền tảng

  • Horizontal scaling: thêm nhiều instance sau load balancer. Điều kiện quan trọng là state đã nằm trong database/Redis/checkpointer dùng chung.
  • Scale theo concurrency/queue depth: agent có thể chờ LLM nên CPU thấp không có nghĩa là hệ thống còn rảnh.
  • Health probe: liveness (còn sống), readiness (nhận traffic được), startup (khởi động xong).
  • Graceful shutdown: khi nhận SIGTERM, ngừng nhận việc mới và drain request đang chạy; agent turn dài cần đủ thời gian hoàn tất.
  • Zero-downtime deployment: chạy version mới → đợi health check pass → chuyển traffic → drain và dừng version cũ.
Router/failover: khi model/provider rate-limit hoặc lỗi, có thể chuyển sang provider/model dự phòng. Retry phải có backoff và giới hạn; retry vô hạn là rủi ro chi phí.

10. Production nâng cao — các ý đáng nhớ

Idempotency và durable execution

Timeout không phân biệt được “hành động thất bại” với “hành động thành công nhưng phản hồi về chậm”. Nếu agent retry gửi email, tạo ticket hoặc trừ tiền mà không có cơ chế idempotent, side effect có thể xảy ra hai lần.

Idempotency key

Gắn key ổn định (ví dụ order_id hoặc UUID) cho hành động có side effect. Retry cùng key nên không tạo hành động trùng.

Durable execution

Ghi lại state/đầu ra từng bước để resume sau crash thay vì chạy lại mọi thứ. Hành động ở hệ thống ngoài vẫn cần idempotency.

Saga cho chuỗi hành động

Nếu workflow có nhiều bước và một bước sau thất bại, cần các hành động bù (compensation) cho bước trước nếu có thể. Ví dụ giữ chỗ → thanh toán → xác nhận; nếu xác nhận lỗi, cần hoàn tiền/hủy giữ chỗ theo quy tắc xác định.

Egress, sandbox và least privilege

  • Egress allowlist: giới hạn domain/dịch vụ agent được kết nối, để giảm rủi ro đưa dữ liệu ra ngoài.
  • Sandbox: cô lập filesystem và network; đừng giả định có sandbox chỉ vì đã giới hạn prompt.
  • Least privilege: mỗi agent chỉ có quyền cần thiết; tách identity và quyền đọc/ghi; hành động nguy hiểm phải qua gate/approval.

Self-host model?

Tự phục vụ model có thể phù hợp khi có yêu cầu residency/compliance, cần tùy biến hoặc workload đủ lớn. Nhưng đổi lại, bạn phải quản thêm GPU service, model weights/revision, engine, quantization, cold start, readiness, scaling và rollback. Tự host không có nghĩa là hết vận hành.

Serving concepts từ slide: continuous batching giúp không để GPU chờ request dài nhất; PagedAttention quản lý KV cache theo block; prefix caching giảm tính lại prefix chung; speculative decoding dùng model nháp đề xuất token rồi model đích xác minh; disaggregated prefill/decode tách hai loại workload để scale riêng.

12. Trắc nghiệm tự kiểm tra

Chọn một đáp án cho mỗi câu rồi bấm Chấm điểm. Đọc giải thích cả khi chọn đúng để củng cố khái niệm.

Chưa chấm điểm

1Điểm khác biệt quan trọng của agent so với CRUD app truyền thống là gì?

Agent thường chạy nhiều bước, gọi model/tool, cần giữ memory và phát sinh chi phí token.

2Environment parity có nghĩa là gì?

Môi trường càng giống nhau, lỗi chỉ xuất hiện khi deploy càng ít.

3Container giải quyết vấn đề nào?

Container giúp đóng gói môi trường chạy; không thay thế mọi lớp bảo mật hay kiểm thử.

4Vì sao slide khuyên dùng python:3.12-slim thay vì Alpine cho nhiều dự án ML Python?

Tương thích wheel/package thường thuận tiện hơn với slim; kiểm tra workload thực tế.

5Vì sao container nên chạy bằng user non-root?

USER app giới hạn quyền so với chạy root, làm giảm tác động của sự cố.

6SBOM là gì?

SBOM giúp biết image chứa những package nào; kết hợp scan lỗ hổng và pin digest.

7Health check /healthz thường dùng để làm gì?

Health endpoint giúp nền tảng biết service còn sống hoặc có sẵn sàng nhận traffic hay không.

8Agent request bị 504 sau khoảng 30–60 giây. Điều gì có thể xảy ra?

Agent loop có thể lâu hơn HTTP proxy timeout. Có thể dùng SSE hoặc chuyển sang async job/private route.

9SSE phù hợp nhất với kiểu response nào theo slide?

SSE thường dùng để gửi token theo luồng; cần để ý proxy buffering và heartbeat.

10Khi tác vụ agent quá lâu, mô hình submit-and-poll hoạt động thế nào?

Async job tách thời gian gửi yêu cầu khỏi thời gian xử lý lâu.

11Cách xử lý state để nhiều instance cùng phục vụ một agent?

State ngoài process cho phép request tiếp theo rơi vào instance khác mà vẫn khôi phục hội thoại.

12Agent I/O-bound thường nên scale theo điều gì?

Nhiều request có thể đang đợi LLM trong khi CPU vẫn thấp; CPU đơn thuần có thể không phản ánh tải.

13Liveness và readiness khác nhau thế nào?

Nhầm readiness với liveness có thể tạo restart loop không cần thiết.

14Vì sao API key không được đặt trong biến VITE_* hoặc NEXT_PUBLIC_*?

Đặt key ở backend proxy/BFF và giữ secrets ở server-side.

15“Client-side agent” dùng model frontier thường vẫn cần gì?

Client có thể là UI, nhưng key và chính sách gọi API phải được giữ ở backend.

16Theo slide, trục quan trọng khi chọn cloud cho agent là gì?

Agent có request dài, streaming và state nên giới hạn timeout/runtime rất quan trọng.

17Framework và managed runtime là hai thứ nào?

Chọn framework và runtime độc lập; kiểm tra migration/lock-in trước khi chọn.

18MCP stdio khác remote Streamable HTTP ở điểm nào?

Khi đưa MCP server ra remote, cần xác thực, phân quyền và bảo vệ network/service.

19Bẫy token passthrough trong MCP remote là gì?

Token passthrough có thể phá vỡ audit/rate-limit và tạo rủi ro uỷ quyền sai.

20Trong API gateway, thứ tự kiểm tra hợp lý theo slide là gì?

Reject sớm giúp tiết kiệm token, giảm abuse và chi phí.

21Spend alert có đủ để bảo vệ ngân sách không?

Kiểm tra ngân sách trước mỗi LLM call; alert của provider thường là phản ứng sau.

22CORS có thay thế authentication/authorization không?

API vẫn cần auth và kiểm tra quyền dù đã cấu hình CORS.

23Prompt caching và semantic cache khác nhau ở đâu?

Semantic cache mạnh hơn về matching nhưng có nguy cơ trả câu trả lời cũ/lỗi thời.

24Eval gate trong CI/CD làm nhiệm vụ gì?

Agent có tính không xác định nên cần eval dataset/threshold và so sánh baseline, không chỉ exit code.

25Shadow deployment nghĩa là gì?

Shadow giúp quan sát version mới; phải chặn side effect và nhớ chi phí model có thể tăng.

26Canary deployment khác shadow thế nào?

Canary giới hạn phạm vi ảnh hưởng của bản mới bằng cách tăng traffic từng bước.

27Ba artifact rollback độc lập của agent theo slide gồm gì?

Tách prompt khỏi code giúp rollback prompt/config nhanh mà không cần deploy lại image.

28Vì sao retry tool call có side effect nguy hiểm?

Timeout không cho biết hành động thất bại hay thành công nhưng phản hồi đến chậm; cần idempotency key.

29Idempotency key dùng để làm gì?

Mỗi hành động có side effect nên có key ổn định; kiểm tra trạng thái trước khi retry.

30Tại sao egress allowlist quan trọng với agent?

Giảm nguy cơ data exfiltration, đặc biệt khi agent đọc nội dung không tin cậy và có external communications.

31Mục tiêu của Lab 12 là gì?

Deliverable trong slide gồm Dockerfile multi-stage, compose/.dockerignore, health check + SSE, URL cloud, basic auth và cost guard.
