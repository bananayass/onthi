§3  Kiến trúc Agent

Perceptionuser input, tool results, feedback→ ReasoningLLM core — phân tích trạng thái, chọn bước tiếp→ Actiongọi tool (API/Search) hoặc trả lời user↺ Memorygiữ goal, facts, intermediate results
Chi phí đi kèm kiến trúc4 khối kiến trúc thường kéo theo 4 nhóm cost chính: token · storage · API · latency.

Memory: short-term vs long-term

Short-term memory

  • Nằm trong context window
  • Dùng cho task hiện tại
  • Rẻ, dễ implement — nhưng dễ đầy

Phù hợp khi: cuộc hội thoại ngắn, goal chỉ kéo dài vài bước

Long-term memory

  • Lưu facts, preferences, state ngoài context
  • Có thể là DB, vector store, key-value store
  • Cần retrieval strategy và permission model
Lưu ýKhông phải thêm memory là agent giỏi hơn. Memory chỉ có ích khi chiến lược đọc/ghi và quyền truy cập được thiết kế rõ.

Tool calling = tay chân của agent

  • Tool definitions phải rõ input / output / error mode
  • Agent mạnh lên nhờ tool, nhưng cũng dễ fail hơn vì external dependency
  • Tool calling là cầu nối giữa reasoning trong model và hành động ngoài thế giới thực

§4  ReAct Pattern

Reasoning + Acting — cách đơn giản nhất để biến LLM thành agent có thể debug được.

Thoughttôi đang thiếu gì, nên làm gì tiếp?
→
Actiongọi tool nào, tham số nào?
→
Observationkết quả trả về là gì?
↺
Final Answerkhi đủ thông tin

Lặp đến khi đủ thông tin để trả lời hoặc gặp điều kiện dừng.

Vì sao ReAct mạnhTrace lý do hành động được bộc lộ ra ngoài — giúp con người debug và can thiệp dễ hơn nhiều so với chỉ nhìn final answer.

Trace ví dụ: tìm chuyến bay HAN → HCM

Thought 1
Tôi cần tìm chuyến bay sáng mai từ HAN tới HCM dưới 2 triệu.
Action 1
search_flights(origin="HAN", destination="SGN", date="2026-03-18", max_price=2000000)
Observation 1
Có 2 lựa chọn phù hợp: VietJet 06:10 giá 1.75M, Vietnam Airlines 08:20 giá 1.95M.
Thought 2
User cũng hỏi về trang phục nếu trời mưa. Tôi cần check thời tiết tại HCM.
Action 2
get_weather(city="Ho Chi Minh City", date="2026-03-18")
Observation 2
Nhiệt độ 27–32°C, xác suất mưa 70%.
Thought 3
Tôi đã có cả lựa chọn chuyến bay và dữ liệu thời tiết. Có thể kết luận.
Final Answer
Gợi ý chuyến 06:10 giá 1.75M; mang đồ mỏng, giày dễ khô, ô gấp hoặc áo mưa nhẹ.
Điểm mạnh thật sựKhông chỉ là answer tốt hơn — mà là con người nhìn được agent đã hành động dựa trên quan sát nào.

ReAct tốt ở điểm nào, giới hạn ở đâu?

✓ Ưu điểm

  • Dễ đọc trace và debug
  • Tự quyết được bước tiếp theo từ observation
  • Phù hợp search / booking / investigation / coding
  • Có thể cài safeguard ở từng vòng lặp

✗ Giới hạn

  • Tốn nhiều token và latency hơn chatbot
  • Dễ loop hoặc gọi sai tool
  • Cần eval theo trace, không chỉ final answer
  • Không phù hợp bài toán đơn giản hoặc cần deterministic tuyệt đối
Khi nào nên rời ReAct thủ côngReAct dễ bắt đầu nhất, nhưng khi hệ thống nhiều nhánh hơn, nên chuyển sang graph / state machine rõ ràng.

§5  Từ ReAct đến Function Calling

Năm bước tiến hóa

1. LLM thuầnnext-token prediction→ 2. Prompt Engineeringfew-shot, CoT — vẫn 1 lượt→ 3. ReAct (2022)Thought/Action dạng text tự do→ 4. Function Calling (2023+)JSON schema được train + ép→ 5. Agent hiện nayreasoning + tool call + memory gộp lại
Điểm cần hiểu đúngFunction calling KHÔNG “thay thế” ReAct — vòng lặp Thought/Action/Observation vẫn còn đó, chỉ là Action giờ đáng tin cậy hơn nhiều.

Hạn chế cốt lõi của text-based ReAct

Trong paper gốc, Action chỉ là một chuỗi text theo format cố định (search[entity], lookup[string]) — model phải tự “nhớ” đúng cú pháp, và hệ thống bên ngoài phải parse bằng regex/string matching.

  • Không có schema nào để model hay hệ thống kiểm tra tính hợp lệ trước khi gọi
  • Chỉ cần thiếu dấu hai chấm, sai hoa/thường, hoặc quên "Action Input:" là parser vỡ
  • Model có thể lặp lại Thought/Action cũ mà không tiến thêm (chính paper ReAct cũng ghi nhận)
  • Format dễ trôi (drift) khi đổi model, đổi phiên bản, hoặc đổi prompt — rất khó bảo trì ở production
Gốc rễ vấn đềHệ thống chỉ prompt model trả lời đúng định dạng text, chứ chưa từng gửi cho model một hợp đồng máy đọc được (schema) để bám.

Ví dụ thực tế: khi parser vỡ

# Model output (text tự do):
Thought: Tôi cần tìm chuyến bay HAN-SGN.
action: search_flights("HAN", "SGN")

# Parser (regex chỉ khớp "Action:" viết hoa, đúng format):
ValueError: Could not parse LLM output: missing 'Action:' after 'Thought:'

Model chỉ viết thường action: thay vì Action: — với con người đây là lỗi không đáng kể, nhưng parser dựa trên regex coi là sai hoàn toàn. Không có cơ chế nào để hệ thống “sửa” hay “đoán ý” — cả vòng lặp dừng lại vì 1 ký tự.

Function Calling: cho model một “hợp đồng” rõ ràng

Text-based ReAct

  • Action = chuỗi text tự do
  • Hệ thống tự viết parser
  • Không ai đảm bảo đúng định dạng

Function Calling

  • Dev khai báo tool bằng JSON Schema: tên, mô tả, tham số
  • Model trả về structured object khớp schema
  • Không cần viết regex để đọc output

OpenAI ra mắt function calling tháng 6/2023 cho gpt-4-0613/gpt-3.5-turbo-0613; Anthropic tích hợp tool use tương tự cho Claude. Đây là bước chuyển từ “prompt model trả lời đúng format” sang “model được thiết kế để trả structured output”.

Dev khai báo JSON Schema→ Model nhận schema→ Model trả tool callobject có name + arguments→ Host code validate & execute→ tool result ↺ 
tools = [{
  "type": "function",
  "name": "search_flights",
  "description": "Find flights by route/date/budget",
  "parameters": {
    "type": "object",
    "properties": {"origin": {"type": "string"},
                   "destination": {"type": "string"}},
    "required": ["origin", "destination"],
  },
}]

response = client.responses.create(
    model="gpt-4o", input=messages, tools=tools,
)
for item in response.output:
    if item.type == "function_call":
        print(item.name)       # 'search_flights'
        print(item.arguments)  # '{"origin": "HAN", ...}'

Cơ chế bên trong: hai lớp kết hợp

Lớp 1 · Fine-tuning / RLHF

Model được huấn luyện thêm trên hàng ngàn trajectory “gọi tool đúng cách” — học được khi nào nên gọi tool nào, với tham số gì.

Đây là xu hướng học được, không phải đảm bảo tuyệt đối.

Lớp 2 · Structured Outputs (2024)

JSON Schema được biên dịch thành grammar (finite-state machine); ở mỗi bước sinh token, chỉ token hợp lệ theo schema mới được phép chọn.

Đảm bảo bằng kỹ thuật, không phụ thuộc model “muốn” tuân thủ hay không.

Fine-tuning giúp model chọn đúng tool và đúng lý do (semantic); grammar constraint đảm bảo output luôn parse được (syntactic). Chỉ có lớp 1, model vẫn có thể lệch schema ở edge case hiếm — lớp 2 mới đưa tỷ lệ tuân thủ lên gần như tuyệt đối.

MCP: vì sao cần thêm một lớp chuẩn hóa nữa?

Trước MCP — M×N

Function calling chuẩn hóa cách 1 model gọi 1 tool, nhưng mỗi nhà cung cấp vẫn có thể khác định dạng → phải viết glue code riêng cho từng cặp model-tool.

Sau MCP — M+N

MCP (Anthropic, 11/2024) định nghĩa giao thức chung: server expose tool/data theo 1 chuẩn, client nào cũng kết nối theo đúng chuẩn đó.

Checkpoint: 5 bước tiến hóa

1
LLM thuầnChỉ next-token prediction, không hành động được
2
Prompt engineeringFew-shot/CoT giúp reasoning tốt hơn, nhưng vẫn 1 lượt, không gọi tool
3
Text-based ReAct (2022)Thêm Action dạng text, nhưng phụ thuộc parser tự viết → dễ vỡ
4

5

Cách học đúngMỗi bước giải quyết đúng 1 giới hạn của bước trước — hiểu rõ giới hạn thì hiểu được vì sao ngành thiết kế ra bước tiếp theo, thay vì học thuộc tên công nghệ.

§6  Agent Loop: Code Anatomy

messages = []

for step in range(MAX_ITERATIONS):
    output = call_model(
        system=SYSTEM_PROMPT,
        messages=messages,
        tools=TOOL_REGISTRY,
    )

    if output.is_final:
        return output.text

    result = run_tool(output.name, output.args)
    messages += [
        assistant_tool_call(output),
        tool_message(output.name, result),
    ]

return "Reached max iterations — fallback"

Max Iterations Safeguard — tránh agent đi vòng

Cần guardrails gì?

  • Giới hạn số vòng lặp
  • Timeout cho từng tool
  • Budget token / cost trần
  • Retry có kiểm soát
  • Fallback sang human hoặc chatbot

Dấu hiệu loop

  • Lặp lại cùng một tool call
  • Hỏi lại thông tin đã có
  • Reasoning không tiến thêm
  • Observation không thay đổi nhưng vẫn tiếp tục
Điều kiện dừngKhi output không tiến triển, cùng một tool bị gọi lặp lại, hoặc observation không đổi mà agent vẫn tiếp tục → cần dừng loop và fallback.

Từ ReAct thủ công đến LangGraph

User Input→ LLM Nodetool call → Tool Nodeobservation ↺ continue Final Answerdone
  • ReAct loop bằng tay phù hợp để học bản chất
  • LangGraph giúp biểu diễn state, nodes, edges, conditional routing rõ hơn
  • Khi workflow nhiều nhánh hoặc cần persist state, graph approach dễ maintain hơn loop ad-hoc

Function calling KHÔNG thay thế ReAct — loop vẫn còn, Action đáng tin hơn

Vì sao ReAct text vỡ

Action = chuỗi text search[entity], hệ thống parse bằng regex

  • Không có schema để validate trước
  • Thiếu dấu :, sai hoa/thường → parser vỡ
  • Model lặp Thought/Action cũ không tiến
  • Format drift khi đổi model/prompt

Lỗi kinh điển: Could not parse LLM output

Function Calling

Dev khai báo JSON Schema → model nhận → trả object có name + arguments → host validate & execute

OpenAI 6/2023 (gpt-4-0613). Chuyển từ “prompt trả đúng format” sang “model được thiết kế để trả structured output”

2 lớp cơ chế

Lớp 1 · Fine-tuning — train trên hàng ngàn trajectory gọi tool → chọn đúng tool, đúng lý do (semantic). Là xu hướng học được, không đảm bảo tuyệt đối.

Lớp 2 · Structured Outputs (2024) — schema → grammar (FSM), chỉ token hợp lệ mới được sinh → output luôn parse được (syntactic). Đảm bảo bằng kỹ thuật.

Số liệu then chốt

100% tuân thủ schema (gpt-4o-2024-08-06 + Structured Outputs)
< 40% (gpt-4-0613 không có cơ chế này)

Agent loop code

for step in range(MAX_ITERATIONS):
    output = call_model(system, messages, tools)
    if output.is_final: return output.text
    result = run_tool(output.name, output.args)
    messages += [assistant_tool_call(output),
                 tool_message(output.name, result)]
return "Reached max iterations — fallback"
