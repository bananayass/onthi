§2  Agent Memory Architecture

Memory không chỉ là lưu nhiều hơn; nó là quyết định xem agent được nhớ gì, quên gì, và truy gì khi cần.

Short-term Memory

  • Nằm trong context window
  • Giữ lịch sử gần đây và task hiện tại
  • Rẻ để dùng, nhưng dễ đầy token
  • Phù hợp cho session logic ngắn

Long-term Memory

  • Nằm ngoài context window
  • Thường là vector store, DB, profile store
  • Phải truy xuất khi cần
  • Phù hợp cho tri thức tích lũy và user history chọn lọc
Câu chốtContext window KHÔNG phải là vector store. Agent chỉ “nhớ dài hạn” khi có cơ chế truy xuất hoặc lưu trữ bên ngoài.

§3  Chunking

Chunk là đơn vị nhỏ nhất mà agent thật sự truy xuất; cắt sai ở đây thì mọi bước sau đều trả giá.

Vì sao phải chunk?

  • Embedding model có giới hạn token input
  • 1 file dài → 1 vector: chỉ tìm được file, không tìm được đoạn liên quan
  • Chunk nhỏ → retrieval chính xác hơn, inject ít nhiễu hơn
  • Đưa quá nhiều context không liên quan làm giảm chất lượng câu trả lời — model bị phân tán, tốn thêm token và latency

Quá to hay quá nhỏ đều trả giá

✗ Chunk quá to

Dính nhiều chủ đề vào cùng một vector — retrieve trúng nhưng inject rất nhiễu.

> 1000 tokens

✓ Chunk hợp lý

Một ý / một section trọn vẹn, có overlap 10–15% giữa các chunk.

200–500 tokens

✗ Chunk quá nhỏ

Mất ngữ cảnh, retrieve nhiều mảnh rời rạc, khó tổng hợp.

< 50 tokens
Mẹo overlapKhi cắt chunk, lấy thêm 1–2 câu cuối của chunk trước làm phần đầu chunk sau — giúp giữ ngữ cảnh tại điểm cắt.

Ví dụ: cùng một FAQ, ba cách chunk — query “đổi size”

Hợp lý“Q2: Đổi size được không? A2: Được, trong vòng 30 ngày kể từ ngày mua.”LLM trả lời chính xác
Quá nhỏ“Trong 30 ngày.” hoặc “Q2: Đổi size được không?”Thiếu ngữ cảnh, LLM không đủ thông tin

Cây quyết định chọn chunking

1

2

3

4

Cosine hay Euclidean?

Câu hỏi gốc: “độ lớn của vector có mang thông tin cần so sánh hay không?”

Dùng COSINE khi…

Chỉ quan tâm nội dung / hướng, không quan tâm độ lớn — dữ liệu dài ngắn rất khác nhau nhưng cùng chủ đề. Vector thưa, nhiều chiều: text embedding, TF-IDF, user preference.

VD: “hoàn tiền” (5 từ) vs cả trang policy hoàn tiền → cosine vẫn thấy giống nhau.

Dùng EUCLIDEAN khi…

Độ lớn là thông tin thật, không phải nhiễu, và các chiều cùng đơn vị / cùng scale. Cần khoảng cách tuyệt đối: toạ độ, cảm biến, image feature, clustering (k-means).

VD: hai điểm GPS — 2 km và 200 km khác nhau thật, không được chuẩn hóa mất.

Quy tắc thực dụngKhi vector đã normalize về độ dài 1, cosine và Euclidean xếp hạng giống nhau. Phần lớn embedding model hiện đại đều trả vector đã normalize → mặc định cứ dùng cosine cho text.

§5  Vector Store

Vector store không chỉ lưu vector; nó lưu cả nguồn, metadata, và khả năng lọc để retrieval có ngữ cảnh đúng.

Mỗi record gồm 4 thành phần

01
ID

Định danh record

02
Original chunk

Text gốc — dùng để inject vào prompt

03
Embedding vector

Dùng để tìm (semantic search)

04
Metadata

Key-value: source, category, access…

Phân biệt quan trọngVector dùng để TÌM. Chunk dùng để INJECT vào prompt cho LLM. Hai thứ khác nhau, lưu cùng nhau.
(Search results top-k là output khi query, không phải thứ được lưu.)

3 tham số điều khiển retrieval

Tham sốÝ nghĩaVí dụ
Top-kLấy bao nhiêu chunk gần nhấtn_results=3: đủ cho câu hỏi đơn · n_results=10: khi cần tổng hợp nhiều nguồn
Score thresholdBỏ chunk có cosine thấp hơn ngưỡng0.7: chỉ giữ chunk thật sự liên quan · 0.4: chấp nhận liên quan nhẹ
Attribute filterLọc theo metadata TRƯỚC KHI searchwhere={"category": "support"}: chỉ tìm trong tài liệu CS
Công thức thực dụngFilter theo category trước → semantic search → lấy top-3 có score > 0.6.
Retrieval tốt = chunk đúng + metadata đủ + filter hợp lý — không phải đổi model.

Toàn cảnh ingestion pipeline — 3 khối lớn

KHỐI 1
Input Control

Chọn & kiểm soát nguồn. Nguồn nào được index? Nhận diện MIME type → mở file → chọn extractor đúng. Ai sở hữu? PII? Access level?

KHỐI 2
Processing Pipeline

Làm sạch & chuẩn hóa. OCR/extract → clean header, footer, rác → structure → Markdown + metadata

KHỐI 3
Indexing Pipeline

Cắt, embed, lưu. Chunking → embed → store (vector + chunk + metadata) → verify

Nguyên tắc debugLỗi retrieval thường KHÔNG sinh ra ở khối 3. Nó sinh ra ở khối 1 (index sai nguồn) hoặc khối 2 (bỏ bước clean) — nhưng chỉ lộ ra khi query.
→ Debug thì đi ngược từ 3 về 1.

Input Control — nhận diện MIME & chọn extractor

File / URL→ Detect MIME type→ Mở file (validate)→ Chọn extractorpdf → PDF parser · officedocument → docx · image/* → OCR · text/html → HTML → MD

Đừng tin phần mở rộng file

.pdf có thể là scan ảnh; .txt có thể là JSON; .doc có thể là RTF. Kiểm tra magic bytes / MIME thật, không chỉ đọc đuôi file.

Fail nhanh, ghi log rõ

Không có extractor → bỏ qua và log, đừng index rác. Ghi lại mime, extractor, status vào metadata để debug về sau.

Sai lầm phổ biếnBỏ qua bước Clean & Structure, đưa raw text thẳng vào chunking. Kết quả: chunk chứa header/footer rác, OCR lỗi, ký tự đặc biệt — retrieval quality giảm rõ rệt.

§7  Kết nối Agent với Data

Retrieval pipeline là chiếc cầu nối giữa dữ liệu riêng và hành vi của agent.

OFFLINE · IngestionDocument → Chunk → Embed → Store ······· ONLINE · RetrievalQuery → Embed → Search → Inject → LLM
Hai pha tách biệtIngestion chạy offline khi dữ liệu thay đổi. Retrieval chạy online mỗi khi user hỏi.

Retrieval khác gì Memory?

Retrieval

  • Tìm context liên quan cho câu hỏi hiện tại
  • Đọc từ knowledge base
  • Trọng tâm: relevance và grounding

VD: hỏi “chính sách đổi trả” → tìm trong FAQ → trả lời dựa trên tài liệu.

Memory

  • Lưu trạng thái, sở thích, lịch sử chọn lọc
  • Từ user profile hoặc interaction history
  • Trọng tâm: continuity và personalization

VD: nhớ user lần trước đã đổi size M → gợi ý “đổi lại size khác?”

Nhiều hệ thống dùng cả hai: retrieval để biết domain facts, memory để biết user này là ai và đã làm gì trước đó.

Failure demo: chunk xấu vs chunk tốt

Query: “Chính sách đổi trả áp dụng trong bao lâu?”

✗ Chunk xấu (raw, không section)

Retrieved (cosine 0.61): “…giao hàng miễn phí đơn trên 500k. Đổi trả trong 30 ngày. Liên hệ hotline 1900…”

LLM: “Bạn có thể đổi trả và liên hệ hotline 1900…” (nhiễu, thiếu chi tiết)

✓ Chunk tốt (theo section + metadata)

Retrieved (cosine 0.89): “Chính sách đổi trả: Khách hàng có 30 ngày kể từ ngày nhận hàng. Sản phẩm phải còn nguyên tem.”

LLM: “30 ngày kể từ ngày nhận, sản phẩm còn nguyên tem.” (chính xác, có nguồn)

§8  Key Takeaways

1 · Data qualityThường quan trọng hơn đổi sang model đắt hơn.
2 · EmbeddingLà lớp dịch ngôn ngữ sang không gian có thể so sánh nghĩa.
3 · Vector storeLà bộ nhớ dài hạn có thể tìm kiếm bằng ngữ nghĩa và metadata.
4 · Retrieval pipelineLà cầu nối từ dữ liệu riêng tới câu trả lời grounded của agent.

Chunking — chuyên biệt

Parent-child
Search chunk nhỏ, inject chunk cha. Rất phổ biến production
Hierarchical
doc summary → section → paragraph
Code-aware
Cắt theo hàm/class bằng AST
Table-aware
Giữ bảng, kèm header dòng

Cây quyết định chunking

  • Có heading tốt → Heading/structural
  • Văn bản chảy dài → Recursive → Semantic
  • LLM thiếu ngữ cảnh → Parent-child / Sentence-window
  • LLM bị nhiễu → chunk nhỏ hơn / Proposition
  • Corpus lớn + câu hỏi tổng hợp → Hierarchical

Embedding là gì

Hàm biến text/ảnh/audio → vector cùng kích thước (vd 1536 chiều).
Đo khoảng cách giữa vector = đo độ giống nhau về nghĩa.

Cosine vs Euclidean

Hỏi: “độ lớn vector có mang thông tin không?”

Cosine — chỉ quan tâm hướng/nội dung. Text embedding, TF-IDF

Euclidean — độ lớn là thông tin thật, cùng scale. GPS, cảm biến, k-means

Vector đã normalize → hai cái xếp hạng giống nhau → mặc định cosine cho text
