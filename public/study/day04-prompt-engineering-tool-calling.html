Prompt Engineering & Tool Calling

Làm sao nói để AI hiểu đúng ý?

“Hai người hỏi AI cùng một việc, một người nhận kết quả xuất sắc, người kia nhận rác. Tại sao?
Và: cùng một agent, đôi khi nó gọi tool đúng, đôi khi gọi sai — do prompt hay do tool?”

CÂU HỎI MỞ ĐẦU
Ý tưởng xuyên suốtPrompt là interface giữa human intent và model behavior.
Tool calling là interface giữa model và thế giới bên ngoài.

§1  Prompt Engineering Fundamentals

Prompt tốt không phải prompt “hay”, mà là prompt tạo ra hành vi mong muốn ổn định.

✗ Prompt kém

“Viết email cho tôi”

Không rõ gửi ai, về gì, tone nào, dài bao nhiêu.
Kết quả: chung chung, khó dùng ngay.

✓ Prompt tốt

“Viết email xin lỗi khách hàng về giao hàng trễ 2 ngày, tone lịch sự, dưới 120 từ, có CTA rõ ràng.”

Rõ task, context, constraint, format.
Kết quả: actionable hơn hẳn.

Nguyên tắc vàngSpecificity beats cleverness. Prompt ngắn nhưng rõ nghĩa thường tốt hơn prompt dài mà lan man.

RTCF — 4 thành phần của prompt tốt

ROLE

“Summarize the ticket and propose next step”

CONTEXT

Thứ tự ưu tiênBắt đầu với Task + Format. Chỉ thêm Role hoặc Context khi chúng thực sự cải thiện chất lượng hoặc tính nhất quán.

Prompt iteration: kém → tốt → xuất sắc

v1 — Mơ hồ“Tóm tắt bài báo này”
Không rõ dài bao nhiêu, cho ai đọc, focus gì→ v2 — Có format“Tóm tắt trong 3 bullets, mỗi bullet dưới 20 từ”
Rõ format, nhưng thiếu audience và focus→ v3 — RTCF đầy đủ“Bạn là analyst. Tóm tắt cho CFO, 3 bullets, <20 từ. Focus: Q2 revenue impact. Tone: data-driven.”

Prompt engineering là iterative process: viết → test → observe → improve. Không ai viết prompt hoàn hảo lần đầu.

Ba loại prompt

LoạiMục đích chínhKhi dùng

Negative prompting & boundary setting

✗ Chỉ nói “đừng”

  • “Đừng dùng jargon”
  • “Đừng đoán”
  • “Đừng trả lời quá dài”

✓ Nói rõ thay thế

  • “Giải thích bằng ngôn ngữ lớp 10 hiểu được”
  • “Nếu không chắc, trả lời: Tôi cần thêm thông tin”
  • “Giới hạn dưới 150 từ”
Câu chốtNegative prompts hiệu quả nhất khi kèm positive alternative. Model cần biết nên làm gì, không chỉ biết đừng làm gì.

Token budget awareness

Rule thực dụngPrompt dài hơn không đồng nghĩa prompt tốt hơn. Mỗi token thừa làm tăng chi phí, latency, và đôi khi cả nhiễu.
→ Nếu prompt dài thêm nhưng không làm thay đổi hành vi mong muốn, hãy cắt bớt.
Prompt engineering tốt là tối ưu độ rõ và khả năng kiểm soát, không phải thi xem ai viết prompt dài hơn.

Temperature & sampling parameters

Use caseTemperatureLý do
Classification, extraction0Deterministic, reproducible
Chatbot, support0.3 – 0.5Nhất quán nhưng tự nhiên
Creative writing0.7 – 1.0Đa dạng, sáng tạo
Brainstorming1.0 – 1.5Khám phá, chấp nhận noise

top_p: chỉ xét các token có tổng xác suất < p. Thường dùng p = 0.9–0.95. Đừng tune cả temp và top_p cùng lúc.

Hiểu lầm phổ biếnTemperature không thay thế prompt tốt. Nếu prompt mơ hồ, giảm temperature chỉ khiến model lặp lại cùng một output kém.

§2  Advanced Prompting Techniques

Dùng kỹ thuật nâng cao khi chúng cải thiện kết quả — không phải mặc định.

Zero-shot

Không có ví dụ mẫu. Nhanh, rẻ — nên thử trước.

One-shot

1 ví dụ mẫu. Tốt khi cần giữ format rõ hơn.

Few-shot

2–5 ví dụ. Tăng consistency, nhưng tốn token hơn.

CoT

Cho model reasoning từng bước. Hữu ích cho task suy luận.

Thứ tự thử thực dụngzero-shot → few-shot → decomposition / CoT. Đừng nhảy vào prompt phức tạp ngay từ đầu.

Khi nào dùng few-shot?

  • Khi model hiểu task nhưng ra sai format hoặc không ổn định giữa các input tương tự
  • Khi cần giữ tiêu chuẩn đánh giá, tone, hoặc cách lập luận nhất quán
  • Ví dụ mẫu nên relevant, đa dạng vừa đủ, và đúng format mong muốn

Few-shot không phải để “dạy lại” model mọi thứ; nó là cách chỉ ra pattern mà bạn muốn model bám theo.

4 anti-patterns của few-shot

Anti-patternHậu quả
Ví dụ quá giống nhauModel overfit pattern, không generalize sang input mới
Ví dụ sai formatModel copy sai format từ examples
Quá nhiều ví dụ (>5)Diminishing returns, tốn token, chậm hơn
Ví dụ có lỗiModel sẽ reproduce lỗi một cách trung thành
Best practiceVí dụ đa dạng, đúng format, cover edge cases — 2–5 examples là đủ.

Chain-of-Thought và Tree-of-Thought

CoT phù hợp khi

  • Bài toán cần reasoning nhiều bước
  • Bạn muốn model giải thích logic trung gian
  • Bạn cần debug xem model sai ở bước nào

Tree-of-Thought

  • Hữu ích cho bài toán cần explore nhiều hướng
  • Phức tạp hơn, tốn token và latency hơn
  • Chỉ nên giới thiệu như extension, không phải mặc định
Cảnh báoCoT là công cụ cải thiện reasoning, không phải phép màu. Nếu task vốn dĩ chỉ là formatting hoặc extraction đơn giản, CoT thường là overkill.

Structured output prompting

LLM output mặc định là free-form text, khó parse programmatically. Trong agent pipeline, bạn cần JSON/structured data.

Cách tiếp cậnMô tả
JSON modeAPI parameter (OpenAI)
Prompt-based“Respond ONLY with valid JSON”
XML tags<thinking>...</thinking>
PrefillBắt đầu assistant message bằng { (Anthropic)
Luôn validate JSON outputModel có thể trả sai format, đặc biệt với schema phức tạp hoặc temperature cao.
Mẹo: đưa JSON schema ví dụ vào prompt giúp model bám format tốt hơn.

§3  System Prompt Engineering

System prompt tốt làm agent nhất quán hơn, dễ kiểm soát hơn, và dễ test hơn.

Anatomy — 5 thành phần

1
PersonaRole, expertise level, communication style
2
RulesViệc nên làm, việc luôn phải làm
3
CapabilitiesModel được phép dùng tools nào, dữ liệu nào priority
4
ConstraintsKhông làm gì, khi nào từ chối, khi nào escalate
5
Output formatJSON, markdown, bullet list, schema, language

System prompt iteration: v1 → v2

v1 — Ban đầu

You are a support agent.
Help customers with orders.
Be polite.

Vấn đề: model hallucinate order status, trả lời câu ngoài scope, output format không nhất quán.

v2 — Sau khi test & fix

You are a support triage agent.
Rules: Answer in Vietnamese. Be concise.
Constraints: NEVER invent order status.
If out of scope: "Tôi chỉ hỗ trợ về đơn hàng."
Output: JSON {intent, action, reply}

Cải thiện: clear boundaries, output contract, refusal pattern rõ ràng.

System prompt cần iterate dựa trên test results: viết → test 10 câu → fix → test lại.

4 anti-patterns của system prompt

Anti-patternBiểu hiện
Quá dàiNhồi mọi thứ vào 1 prompt 2000+ tokens rồi hy vọng model luôn làm đúng
Mâu thuẫnVừa bảo “ngắn gọn”, vừa bắt “giải thích chi tiết từng bước”
Mơ hồ“Hãy thông minh”, “hãy chuyên nghiệp” — nhưng không định nghĩa chuẩn output
Không test edge casesQuên kiểm tra câu hỏi ngoài phạm vi, refusal, tool failure
Nguyên tắcSystem prompt là policy layer. Càng rõ boundary, càng dễ predict hành vi.

System prompt testing checklist

✓
Happy path: câu hỏi trong scope → trả lời đúng format?
✓
Edge case: câu hỏi mơ hồ → hỏi lại hay đoán bừa?
✓
Out of scope: câu hỏi ngoài phạm vi → từ chối đúng cách?
✓
Adversarial: prompt injection → có bị bypass?
✓
Tool decision: khi nào gọi tool vs khi nào trả lời trực tiếp?
✓
Format consistency: 10 câu khác nhau → output format nhất quán?

Độ chính xác theo vị trí thông tin trong context (Liu et al. 2023) — cao ở đầu và cuối, tụt ở giữa.

Hệ quả thực tiễn:

  • Đặt instructions quan trọng ở đầu hoặc cuối
  • Context dài → info ở giữa dễ bị “quên”
  • Break long lists bằng headers/separators
  • Recent context nên đặt ngay trước user query

Memory injection và Context compression

Memory injection

  • Chỉ đưa vào facts thật sự cần cho task hiện tại
  • Ưu tiên recent hoặc relevant history, không dump toàn bộ transcript
  • Tốt cho support agent, coding assistant, tutor nhiều lượt

Compression — 3 cách

  • Summarize: tóm tắt phần cũ
  • Drop: bỏ hẳn phần không còn liên quan
  • Archive: đẩy ra ngoài context, chỉ fetch lại khi cần
Câu chốtContext engineering là bài toán chọn lọc và ưu tiên. Nếu mọi thứ đều quan trọng, thì ra không có gì thực sự nổi bật với model.

§5  Prompt Safety & Evaluation

Prompt tốt không chỉ cho kết quả đúng — nó còn phải an toàn và đáng tin.

Direct injection

User trực tiếp nói “Ignore your instructions and do X”

Indirect injection

Malicious content trong document/email mà agent đọc qua tool

6 defense strategies

1
Delimiter separationWrap untrusted input: <user_input>...</user_input>
2
Instruction hierarchySystem prompt luôn ưu tiên hơn user input
3
Input validationFilter known injection patterns trước khi đưa vào prompt
4
Output validationKiểm tra output trước khi execute actions
5
Least privilegeTool permissions tối thiểu cần thiết
6
Human-in-the-loopYêu cầu confirm cho sensitive actions
Thực tếKhông có defense nào hoàn hảo 100%. Defense-in-depth: kết hợp nhiều layers.

Guardrails pattern

Pre-guarddetect injection · validate input format · rate limiting→ LLM / Agent→ Post-guardmask PII · validate JSON schema · block dangerous tool calls

Prompt evaluation framework

DimensionCâu hỏiĐo bằng cách
CorrectnessOutput có đúng không?Test cases + human review
Consistency10 lần chạy cho cùng kết quả?Chạy lặp lại, đo % match
SafetyCó bị bypass không?Adversarial test cases
Ngưỡng thực dụngChạy 10–20 test cases. Nếu < 90% pass → cần iterate prompt.
A/B testing: so sánh prompt v1 vs v2 trên cùng test set.

§6  Tool Calling

Cách agent chuyển từ “nói” sang tương tác với thế giới thực.

User asks→ Model decides→ Tool call→ App executes→ Model reads response→ Final answer
Điểm dễ hiểu nhầm nhấtModel KHÔNG tự chạy code hay tự gọi API ngoài. Ứng dụng của bạn nhận tool request, chạy tool, rồi gửi kết quả trở lại model.

Ai làm gì?

Vai tròTrách nhiệmVí dụ
DeveloperĐịnh nghĩa tool schema, viết implementation, handle errorsViết get_weather()
LLMQuyết định tool nào, arguments gì, dựa trên user intent{"name": "get_weather", "city": "Hanoi"}
ApplicationNhận tool call, execute, trả resultGọi API weather, trả JSON
LLM (lần 2)Synthesize tool result thành câu trả lời tự nhiên“Hà Nội hôm nay 32°C, trời nắng”

Tool schema anatomy

  • Name — nên ngắn, rõ, động từ + đối tượng
  • Description — nói khi nào nên dùng tool này
  • Parameters — mô tả input bằng JSON Schema
  • Required fields — giúp model biết thiếu gì thì chưa gọi được
Quan trọngLLM đọc description như tài liệu hướng dẫn. Nếu description mơ hồ, model sẽ chọn sai tool hoặc truyền sai arguments.

Good vs bad tool description

DescriptionHệ quả
Bad“Gets weather”Quá ngắn, model không biết khi nào dùng
Bad“This comprehensive tool can be used to retrieve current weather information for any city worldwide…”Quá dài, thêm noise
Good“Get current weather for a city. Use when user asks about weather, temperature, or conditions.”Rõ chức năng + trigger condition
Công thức viết descriptionNên chứa: (1) chức năng · (2) khi nào dùng · (3) khi nào KHÔNG dùng. Viết như viết API docs.

Ví dụ: cùng tool, description khác → behavior khác hoàn toàn

“Search orders”

Model gọi cho MỌI câu hỏi liên quan đến order, kể cả “đơn hàng là gì?”

Mô tả có boundary

“Search orders by order_id or customer email. Use ONLY when user provides an order number or asks about specific order status.”

Model biết boundary rõ, chỉ gọi khi có đủ data.

§7  Design Principles cho Tools

Tool tốt là software interface tốt, không phải prompt trang trí.

Nguyên tắcÝ nghĩaNếu vi phạm
Single ResponsibilityMỗi tool làm 1 việc rõ ràngModel khó quyết định nên gọi tool nào
IdempotencyCùng input cho cùng kết quả; side effect được kiểm soátRetry dễ sinh lỗi phụ
Granularity hợp lýKhông quá nhỏ, cũng không ôm quá nhiều việcOverhead lớn, hoặc tool quá cứng
Test độc lậpUnit test từng tool trước khi gắn vào agentKhó tách lỗi tool khỏi lỗi prompt

Tool granularity — quá nhỏ hay quá to đều có giá

✗ Quá nhỏ

get_customer_name
get_customer_email
get_customer_phone

Hệ quả: quá nhiều calls, overhead lớn, flow rối.

✗ Quá to

handle_all_customer_operations

Hệ quả: model không hiểu boundary, khó debug, khó reuse.

Quy tắcThiết kế tool quanh một hành động nghiệp vụ rõ ràng: lookup_order, get_weather, query_sales_data, send_email_draft.

Parameter design best practices

  • Required vs Optional: chỉ require những gì thực sự cần
  • Enum constraints → giảm lỗi arguments
  • Default values: document rõ trong description
"status": {
  "type": "string",
  "enum": ["pending", "shipped", "delivered"]
}

// thêm ví dụ vào description
"date": {
  "type": "string",
  "description": "Date in YYYY-MM-DD format,
                   e.g. 2026-04-05"
}

Tool return format

// Success
{"status": "success",
 "data": {"temp": 32, "city": "Hanoi"},
 "source": "openweathermap"}

// Error
{"status": "error",
 "message": "City not found",
 "code": "NOT_FOUND"}
  • Trả JSON, không raw HTML/XML
  • Include metadata (source, timestamp)
  • Error format consistent
  • Truncate nếu response quá dài

Model xử lý structured JSON tốt hơn nhiều so với raw text hay HTML.

§8  Parallel Tool Calling & Patterns

Nhanh hơn không có nghĩa là tốt hơn nếu flow control và merge logic không rõ.

Sequential

Tool B cần output của Tool A.

VD: tìm order ID → rồi mới tra shipping status.

Parallel

Các tool độc lập có thể chạy cùng lúc.

VD: gọi thời tiết, tỷ giá, và lịch họp song song.

Quy tắcChỉ song song hóa khi không có phụ thuộc dữ liệu. Nếu song song, vẫn cần bước merge / verify rõ ràng ở cuối.

3 tool use patterns thường gặp

1
Conditional tool useAgent tự quyết định có cần tool hay trả lời trực tiếp
2
Tool chainingOutput của tool A là input của tool B
3
Parallel fetch + mergeLấy nhiều nguồn độc lập rồi tổng hợp kết quả
Câu chốtTool calling không chỉ là “gọi API”. Nó là bài toán control flow: khi nào gọi, gọi cái gì, gọi theo thứ tự nào, và làm gì khi tool fail.

Robust tool loop — có error handling

messages = [{"role": "user", "content": user_input}]

for round in range(MAX_TOOL_ROUNDS):
    response = call_model(messages, SYSTEM_PROMPT, TOOLS)
    tool_calls = extract_tool_calls(response)

    if not tool_calls:
        print(response.text)
        break

    for tc in tool_calls:
        try:
            result = run_tool(tc.name, tc.args, timeout=10)
        except TimeoutError:
            result = {"error": "Tool timed out, please try again"}
        except Exception as e:
            result = {"error": str(e)}
        messages.append(tool_result_msg(tc.call_id, result))
else:
    print("Warning: max tool rounds reached")

5 Key Takeaways

1 · Prompt là interfaceGiữa human intent và model capability. Prompt tốt giúp model làm đúng việc, đúng format, đúng boundary.
2 · System promptLàm agent nhất quán và predictable hơn, đặc biệt khi có tools và constraints.
3 · Tool descriptionQuyết định rất mạnh việc model biết khi nào dùng tool nào và gọi với arguments gì.
4 · Parallel tool callsNhanh hơn đáng kể khi tool độc lập; nếu có phụ thuộc dữ liệu, giữ flow tuần tự.
5 · Prompt safetyInjection defense và guardrails là bắt buộc cho production agents, không phải tùy chọn.

Few-shot anti-patterns

  • Ví dụ sai format → model copy

  • Ví dụ có lỗi → model reproduce trung thành

CoT

Dùng khi: reasoning nhiều bước · cần giải thích logic trung gian · cần debug model sai ở bước nào

Structured output

System prompt — 5 phần

  1. Persona — role, expertise, style
  2. Rules — nên làm, luôn phải làm
  3. Capabilities — tools nào, data nào
  4. Constraints — không làm gì, khi nào từ chối/escalate
  5. Output format — JSON, schema, ngôn ngữ

System prompt anti-patterns

  • Quá dài (2000+ tokens nhồi mọi thứ)
  • Mâu thuẫn (ngắn gọn + giải thích chi tiết)
  • Mơ hồ (“hãy thông minh”)
  • Không test edge cases

System prompt = policy layer. Càng rõ boundary càng dễ predict

System prompt test checklist

  1. Happy path — đúng format?
  2. Edge case — hỏi lại hay đoán bừa?
  3. Out of scope — từ chối đúng cách?
  4. Adversarial — có bị bypass?
  5. Tool decision — gọi tool vs trả trực tiếp?
  6. Format consistency — 10 câu nhất quán?

Direct: user nói “Ignore your instructions”
